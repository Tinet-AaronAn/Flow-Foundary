# 长周期流程编排底层能力

本文说明 FlowFoundry **已经具备、可被业务流程直接使用** 的底层编排能力：它们支撑数小时、数天、数周的流程实例，而不是秒级工具串联。

实现细节、字段与 API 不在本文展开，请按文末「相关文档」下钻。

---

## 1. 这份能力解决什么问题

Dify / n8n 一类工具编排擅长短流程、API 串联和快速试验。企业业务流程（催收多轮、审批、等人、等外部系统、跨天定时）还需要：

| 需求 | 含义 |
|------|------|
| **耐久** | 实例可跨进程重启、Worker 崩溃、集群升级继续跑 |
| **可等待** | 等 Timer、等 Signal、等人工，而不是在 Activity 里 `sleep` |
| **可恢复** | 失败可重试；历史可回放；不必从第一步重跑 |
| **可治理** | 发布版本不可变；运行引用固定版本；可审计 |
| **可隔离** | 多业务 App 的 Namespace / Task Queue 互不影响 |

FlowFoundry 的答案是：**业务画布表达意图，通用解释器调度，Temporal 作为唯一可靠执行内核**。业务人员不需要理解 Workflow、Activity、Task Queue、确定性等概念。

**定位一句话：**

```text
画布编排业务能力 → Flow DSL / Execution Plan → Temporal 可靠执行
副作用全部在 Activity；长等待全部在 Workflow（Timer / Signal / Await）
```

## 2. 能力分层：什么算「底层」

```text
┌─────────────────────────────────────────────────────────┐
│ 产品层（面向业务）                                          │
│ 画布、Palette、Runs / Runtime 视图、人工待办完成             │
└───────────────────────────┬─────────────────────────────┘
                            │ Flow DSL
┌───────────────────────────▼─────────────────────────────┐
│ 平台语义层（本文重点）                                       │
│ Compiler / Interpreter / VariableStore / Registry        │
│ 节点语义：Activity、Gateway、Timer、Human Task、Child WF   │
└───────────────────────────┬─────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────┐
│ Temporal 运行时                                            │
│ History、Timer、Signal、Query、Retry、Child Workflow      │
└─────────────────────────────────────────────────────────┘
```

「底层能力」= **平台语义层 + Temporal 运行时** 提供的、画布节点可以稳定映射上去的能力。  
HTTP 重试、幂等锁、第三方 SDK、限流等 **不是** 画布能力，它们封装在业务 Activity 里。

解释器只认识六种 `NodeKind`：

```text
START | END | ACTIVITY | GATEWAY | INTERMEDIATE_EVENT | CHILD_WORKFLOW
```

Human Task、Script Task 都编译为 `ACTIVITY`，由 `activityType` 区分。

|---|---------|----------------|---------------------|
| 1 | 可靠执行与状态持久化 | 流程跑几天也不丢进度 | Workflow History + Interpreter 状态 |
| 2 | 通用解释器 | 一份画布即可执行，不必为每条流程写 Workflow 代码 | `FlowInterpreterWorkflow` |
| 3 | 编译门禁 + 不可变执行计划 | 非法图进不了运行；已发布版本不被改写 | `FlowCompiler` → `ExecutionPlan` |

| 5 | Activity 调度与 Registry | 画布节点绑定真实业务能力与队列 | Untyped / Router + Registry |
| 6 | 超时与自动重试 | 临时故障自动再试，不必画 try/catch | Activity timeout / retry |
| 7 | 幂等框架 | 重试不会重复扣费、重复外呼 | `IdempotentActivityExecutor` |
| 8 | 长 Timer | 等一段时间或等到某个时刻 | `Workflow.newTimer` |
| 9 | 周期 / 定时启动 | 按 cron 或指定时刻自动开新实例 | Temporal Schedule（Timer Start） |

| 12 | 事件竞态（Event-based Gateway） | 「谁先到走谁」：超时 vs 回复 vs 取消 | Timer + Signal 竞争 |
| 13 | 条件分支与并行 | 排他 / 包容 / 并行分叉汇合 | Gateway + Safe FEEL |
| 14 | 图级循环与节点 Loop | 多轮业务；同一 Task 重复或扫集合 | Gateway 回边 / `flowFoundryLoop` |
| 15 | 变量与映射 | 节点间传状态，Gateway 只读变量选路 | `VariableStore` |
| 16 | 规则计算（Script Task） | 复杂规则下沉到脚本，画布只读结果 | `script-runtime` Activity |
| 17 | Child Workflow | 调用另一条已发布流程，独立 History | Temporal Child Workflow |
| 18 | 运行查询 | 当前节点、等待中的人工任务 | Workflow Query + Runs 读模型 |
| 19 | 双模式执行 | 建模器桩跑通；生产走真实 Activity | `runSource` + DualMode |
| 20 | Namespace 隔离 | 多 App 流程与 Worker 互不串 | 平台 NS = Temporal NS = Registry |
| 21 | 两种交付形态 | 独立 Worker App，或平台托管插件 | SDK Worker / K8s plugin runner |
| 22 | 平台核心 Activity | 任意业务 namespace 都可用人工任务与脚本 | `flowfoundry-platform` 队列 |

## 4. 能力说明

### 4.1 可靠执行与状态持久化

Temporal 记录 Workflow History。解释器每推进一步，进度都在集群里，而不是某个 JVM 的内存里。

因此可以：

- Worker 重启后从 History **回放**到当前节点，再继续。
- 实例存活时间与「HTTP 请求超时」无关，可跨天、跨周。
- 长时间等待（Timer / 人工 / Signal）不占用业务线程空转。

业务运行视图（当前节点、待办、失败原因）由平台 Runs / Runtime 提供；Temporal UI 给开发与运维排查，不作为业务主界面。

### 4.2 通用解释器（Flow Interpreter）

平台用 **一个** Temporal Workflow（`FlowInterpreterWorkflow`）解释所有画布流程：

```text
while 未结束:
  取当前 ExecutionPlan 节点
  按 NodeKind 执行
  写入 VariableStore
  按边条件 / Gateway 选下一跳
```

含义：

- 业务新增一条流程，通常 **不必** 再写一套 Workflow 类。
- 复杂、高度定制的控制流仍可由 FDE 手写 Temporal Workflow（第二条入口），但须遵守同一套 Registry 与治理契约。

解释器 **禁止** 直接访问 DB、HTTP、系统时钟（除 Temporal 提供的确定性时间）、随机数。这些都在 Activity 中。

### 4.3 编译门禁与不可变版本

发布路径：

```text
画布 JSON → Flow DSL → FlowCompiler 校验 → 不可变 Execution Plan → 启动解释器
```

Compiler 是运行前质量门：拓扑非法、Activity 多出边、并行未闭合、FEEL 无法解析等 **不能发布**。

版本规则（平台持久化）：

- Workflow 有 `draft` / `active` / `retired`。
- 已发布版本的 `model_json` **不可变**；改内容须新版本或改 draft。
- 对外按版本启动：`POST /api/workflows/{id}/versions/{version}/run`（仅 `active`）。

长周期实例必须引用 **固定版本**，避免运行中途定义被改写。

### 4.4 确定性、超时、重试、幂等

| 层 | 职责 |
|----|------|
| Workflow / 解释器 | 只做调度与变量；保证 Replay 确定性 |
| Activity | 外部系统、I/O、异常归一化 |
| Temporal Retry | 可恢复技术故障自动再试 |
| 幂等框架 | 同一业务 key 的副作用只生效一次 |

画布 **不** 暴露：HTTP 429 退避、Redis 锁、Worker 崩溃恢复。这些由 Activity 与 Temporal 承担。

业务异常应变成 **结构化结果**（例如「需主管复核」），再由 Gateway / Human Task 表达，而不是把 try/catch 画到图上。

### 4.5 Activity Registry 与动态调度

Registry（`activities-registry.yaml`）是画布与代码之间的契约：`type`、schema、timeout、retry、幂等模板、默认 Task Queue、所属 namespace。

解释器按 `activityType` 找到队列并调度，不写死每一个 Java 方法。业务能力通过：

- 独立 App Worker（`:8082`），或
- 插件包由平台 K8s runner 托管

注册进 Registry 后，即可在对应 namespace 的画布上选用。

**平台内置 Activity**（任意业务 namespace 可用，跑在 `flowfoundry-platform` 队列）：

- `human-task` — 人工任务登记 / 标注
- `script-runtime` — Node.js 脚本规则计算

### 4.6 长等待：Timer

原则：**分钟级以上等待放在 Workflow Timer，禁止 Activity 内 sleep。**

| 节点 | 类型 | 运行时 |
|------|------|--------|
| Intermediate Event | `duration`（相对） / `date`（绝对时刻 + 时区） | `TimerEvaluator` + `Workflow.newTimer` |
| Start Event（`startEventSubtype=timer`） | `cycle` / `date` | Temporal **Schedule** 周期或一次性启动实例 |

Intermediate 的 `value` / `timezone` 支持 `${...}` 变量（例如按 `slot.fixedTime` 等到当天固定时刻）。目标时刻已过时有 `fireImmediately` / `skip` / `fail`。

流程激活时同步 Schedule；停用或删除时暂停 / 删除 Schedule。周期语义在 **Start**，不在流程中间的 Intermediate（中间节点不支持 `cycle`）。

### 4.7 Signal 与事件网关

外部世界把「睡着」的实例叫醒：

- Workflow 提供 `receiveFlowSignal(signalName, payload)`。
- Intermediate Event 可配置 `eventSubtype=signal` + `signalName`。
- **Event-based Gateway**：多条出边各自接到 Timer 或 Signal 事件，**先发生者胜出**，其余路径不执行。

典型：等客户回复 / 等超时升级 / 等人工取消。

Human Task 完成也是 Signal：`completeHumanTask`（`POST /api/flows/runs/{id}/human-task`）。

### 4.8 人机协同（Human Task）

画布只有一种 **Human Task**（编译为 `ACTIVITY` + `human-task`）：

| `mode` | 行为 |
|--------|------|
| `managed`（默认） | 登记待办 → 状态 `WAITING_HUMAN_TASK` → `Workflow.await` 直到完成 Signal |
| `offline` | 只标注「线下已做」（电话、纸质），**不暂停** Workflow |

人工待办、表单、通知、权限在业务侧；平台保证 **暂停与继续** 可跨天、可恢复。可与 Loop 组合：Standard Loop 的每一轮 managed 任务都会再等一次 Signal。

Boundary Event（任务执行期间的超时升级等）为后续版本，当前超时等待用 Intermediate Timer 或 Event-based Gateway 表达。

### 4.9 分支、并行、循环

**Gateway（v1）：**

| 类型 | 语义 |
|------|------|
| Exclusive | 按 Safe FEEL 选 **一条** 路径（无 join） |
| Parallel | 全部分支执行，必须与同类型 join 配对 |
| Inclusive | FEEL 为真的分支执行，join 只等实际激活的分支 |
| Event-based | 事件竞态，无 join |

约束：Activity / Start 均 **单出边**；分支必须经 Gateway。并行区域禁止未闭合、禁止混用 join 类型、v1 禁止嵌套 Parallel split。

**循环两种策略：**

| 策略 | 适用 | 建模 |
|------|------|------|
| 图级循环（推荐多轮业务） | 外呼多轮、退回审批、跨节点状态机 | Exclusive Gateway + 回边 + 变量 |
| 节点 Loop | 同一 Task 按条件或集合重复 | `flowFoundryLoop`：`standard` / 顺序 `multiInstance` |

节点 Loop 仅 ACTIVITY；有 `maxIterations` 上限（默认 100）。并行 Multi-Instance 为后续版本。

### 4.10 变量、FEEL、Script Task

运行时状态集中在 `VariableStore`：

| 命名空间 | 可写 | 含义 |
|----------|------|------|
| `$.input.*` | 否 | 启动入参 |
| `$.vars.*` | 是 | 节点间累积的业务状态 |
| `$.lastResult` | 自动 | 上一 Activity / 人工完成的返回值 |

边上条件编译为 **Safe FEEL AST**，运行期只求值、不重新解析字符串。Gateway **不持参**，只读已有变量。

复杂规则不写在出边上：用 **Script Task** 调 Node.js 脚本服务写入变量，再用 FEEL 选路。脚本调用本身是 Activity，须幂等；已启动实例的 replay 不因脚本文件事后修改而分叉（版本 / hash 审计）。

Child Workflow 的变量 **隔离**，靠 input / output mapping 与父流程交换。

### 4.11 Child Workflow

画布 `kind=workflow` → 独立 Temporal Child Workflow（仍是 `FlowInterpreterWorkflow`，内嵌已编译的 `childExecutionPlan`）。

| | Activity | Sub-process | Child Workflow |
|--|----------|-------------|----------------|
| 语义 | 一个业务动作 | 画布分组，展开进父计划 | 另一条完整流程 |
| History | 父流程内 | 父流程内 | **独立** |
| 版本 | 随父 | 随父 | 可独立发布 |
| 变量 | 同一 Store | 同一 Store | 隔离 + mapping |

父流程 **同步等待** 子流程结束。建模期嵌入子 DSL；运行时不再按 ID 现拉定义。禁止循环引用自身。

### 4.12 查询、审计与联调

- **Query**：Runtime 按 `currentNodeId` / `waitingHumanTaskNodeId` 高亮；Runs 列表可查实例。
- **结构化事件**（设计目标）：节点输入输出、人工操作、脚本 `decisionRef` / `scriptHash`，用于「谁在何时基于什么输入做了决定」。
- **web-modeler vs production**：
  - 联调：`runSource=web-modeler` + 指定 Client 头 → Activity **stub**；Timer **跳过**真实等待；Workflow ID 带 `workflow_test_` 前缀。
  - 生产：强制真实 Activity；忽略客户端 stub 标记。

### 4.13 隔离与交付

**Namespace 三同名、一一对应：** FlowFoundry 逻辑隔离 = Temporal 物理隔离 = Activity Registry 归属。App Worker **不能**自助创建平台 namespace，须管理员登记或本地 bootstrap。

**交付：**

```text
独立 App 仓库
  SDK Worker → Temporal Activity
  SDK Client → 平台 HTTP（禁止浏览器直连 :8081）

或插件包
  同一套 Router + Registry
  平台 K8s runner 托管进程；core 只做控制面
```

停掉插件 Worker 时，Activity 任务在队列中等待；恢复后继续——动态 Activity 启停对长周期实例是安全的。插件内 **手写 typed Workflow** 是例外，升级须遵守 Temporal 版本化约束。

## 5. 场景边界（编排延迟）

解释器把每个 Service / Script Task 映射为一次 Temporal Activity 往返（poll Task Queue，不是进程内函数调用）。

| | 量级（本地未调优，不含业务逻辑） |
|--|--------------------------------|
| 每节点编排税 | 约 **40–70ms** |
| 生产调优后 | 仍约 **15–25ms** / 节点，毫秒级 |

**适合：** 外呼多轮、审批、长 Timer、Signal、跨天实例、单步业务为秒级以上（编排税可忽略）。

**不适合：** 要求节点间 **&lt; 1ms** 的 realtime 控制流；画布上几十上百个无 I/O 细粒度节点还期望「瞬间跑完」；游戏 tick、硬实时设备链。

这类需求应 **合并节点**、在单个 Activity 内批处理，或手写 Temporal Workflow 减少 Activity 次数，而不是把 FlowFoundry 当内存状态机用。

## 6. 与画布节点的对照（便于评审）

```text
Service Task          → Activity（业务 Worker / 插件）
Script Task           → Activity script-runtime（平台队列）
Human Task            → Activity human-task + Await/Signal（或 offline 不暂停）
Exclusive/Inclusive/
Parallel Gateway      → 解释器选边 / fork-join
Event-based Gateway   → Timer + Signal 竞态
Intermediate Timer    → Workflow.newTimer
Intermediate Signal   → receiveFlowSignal
Timer Start           → Temporal Schedule
Child Workflow        → Temporal Child Workflow
Sub-process           → 仅结构展开，无独立运行时
Loop 属性             → 同一 Activity 重复（或改用 Gateway 回边）
```

## 7. 官方示例如何用到这些能力

`examples/ai-collection-strategy`（AI 催收）是长周期场景的参考实现：导入号码、分批、多轮外呼、等待轮次结束、AI 打标、筛选下一轮、结束活动。多轮编排优先 **Gateway 回边 + 变量**；固定时刻下一轮用 **Timer `date` + slot 变量**。Activity 实现与 Registry 在示例模块，不在 `flowfoundry-core`。

## 9. 一句话归纳

FlowFoundry 的长周期编排底层能力，就是把 **可恢复的解释执行**、**可配置的等待（时间 / 信号 / 人）**、**可治理的版本与 Registry**、**可隔离的 Namespace 与 Worker 交付** 叠在 Temporal 上；画布只编排业务，工程复杂度留在 Activity。
